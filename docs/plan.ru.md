# Wordmanner: план продукта

## Задача

Агенты часто пишут формально, дробят мысль на лозунги, избыточно комментируют свою работу и код. Даже хороший персональный профиль не всегда выбирает уместный регистр: письмо коллеге, сообщение в чате, заголовок слайда и техническое объяснение требуют разных решений. Wordmanner даёт короткую инструкцию для агента и локальный слой примеров, который подбирает авторские тексты под конкретную задачу.

Проект пока **не доказал** улучшение качества относительно Claude Styles, Idiolect AI или humanizer skills. Это измеряемая гипотеза. [Обзор конкурентов](../market-research.md) содержит проверенные возможности и ссылки.

## Первые сценарии

1. Агент сообщает о ходе работы только тогда, когда есть полезный факт, и даёт понятный итог.
2. Агент пишет текст презентации с конкретными утверждениями, числами и ограничениями, без рекламной ритмики при обычной рабочей задаче.
3. Агент объясняет техническую тему ясно и оставляет комментарии к коду только там, где они раскрывают причину или нетривиальное ограничение.
4. Агент готовит письмо или чат-сообщение в нужном языке и регистре; личные примеры уточняют стиль, если пользователь их добавил.

## Архитектура

```text
user task + current context
          │
          ▼
      agent skill ───► genre guidance
          │
          ▼
  wordmanner context
          │
          ▼
 local curated samples (~/.wordmanner/ by default)
          │
          ▼
 language + medium filter, then contextual ranking
          │
          ▼
 short prompt with up to 3 examples
```

Импорт и подбор контекста работают локально: CLI не индексирует почту автоматически и не отправляет данные на сервер Wordmanner. Необязательная команда `bench generate` запускает указанную пользователем модель и передаёт ей prompt. По умолчанию примеры лежат в `~/.wordmanner/samples.jsonl` и доступны из разных проектов; путь можно сменить через `WORDMANNER_HOME` или `--store`. Если передать выведенный контекст облачному агенту, выбранные образцы попадут к провайдеру этого агента. Такой выход должен быть виден пользователю и ограничен небольшим числом примеров. В корпус следует включать только собственные исходящие тексты пользователя, отобранные вручную или после предпросмотра импорта. Чужие ответы, подписи из переписки и конфиденциальные сведения следует убрать до импорта. [Поток импорта и границы доверия](import-ux.ru.md) описаны отдельно.

Пользователь может добавлять короткие заметки о предпочтениях в `~/.wordmanner/voice-notes.jsonl` через CLI. Это необязательная память о стиле: формат, язык, желаемая краткость и другие явные правки. Она не требует вести дневник или собирать «second brain» и имеет приоритет над выводами из примеров.

## Срезы разработки

| Этап | Проверяемый результат |
| --- | --- |
| v0.1 — нынешний фундамент | Портируемый skill, локальный импорт JSONL, явный подбор образцов, CLI для слепых сравнений, тесты на изоляцию языков и корректность данных. |
| v0.2 | Расширить нынешний `init --dry-run`/`uninstall` реальной проверкой загрузки skill в Claude Code, Codex, Gemini CLI и Cursor; добавить диагностику версий и конфликтов. |
| v0.3 | Ручная разметка правок и предпочтений; версии профиля; просмотр того, какие образцы попали в prompt и возможность исключить их. |
| v0.4 | Расширить начатый локальный импорт Telegram: одиночные чаты, более точная разметка языка и регистра, просмотр и удаление уже сохранённых примеров. Коннекторы к сервисам — после проверки прав доступа и модели приватности. |
| v0.5 | Локальный MCP поверх того же ядра, только если он улучшает реальное использование в нескольких агентах. |

Этапы можно менять по результатам benchmark. Наличие MCP или hook не является целью само по себе.

## Критерий качества

Сравнивать одинаковую модель на одинаковых заданиях, меняя только воздействие Wordmanner. Отдельно проверять личное сходство, ясность/уместность, сохранение фактов и избыточность. Для презентаций учитывать роль текста на слайде и то, не появились ли новые обещания. Для комментариев к коду учитывать, помогает ли комментарий понять причину, а не только число комментариев. Русский и английский оценивать отдельно. Основной сигнал — слепой выбор человека, дополненный объяснением ошибки; LLM-судьи и детекторы не могут заменить его.

Нужен закрытый набор реальных пользовательских задач и сообщений, разделённый с обучающими образцами по цепочкам и темам. Открытый набор должен содержать созданные для проекта или разрешённые примеры. Публиковать результаты только вместе с версией skill, моделью, параметрами, входами, числом оценок и неопределённостью; результаты из `examples/` не считаются доказательством.
